# Задание 2. Проект архитектуры MVP (To-Be)


## 1. Цели и ключевые требования

1. **Автоматизация записи пациентов**:
  - Пациент может зайти на сайт (портал) и выбрать удобное время, без телефонных звонков.
  - Администратор ресепшена получает уведомление о новой записи и подтверждает её.

2. **Безопасность и конфиденциальность данных**:
  - Система должна обеспечивать шифрование данных при передаче и хранении.
  - Разграничение доступа (RBAC/ABAC), чтобы сотрудники видели только необходимые данные.
  - Должен вестись аудит (логирование) всех операций с конфиденциальными данными.

3. **Масштабируемость и готовность к интеграциям**:
  - Готовность к росту числа пользователей и новых филиалов.
  - Возможность интеграции с лабораториями, мобильным приложением, CRM и т.д.

4. **Политика жизненного цикла данных**:
  - Хранить конфиденциальные данные только столько, сколько требуется по закону.
  - Предусмотреть процедуру удаления (или анонимизации) по истечении сроков или по запросу клиента.

---

## 2. Диаграмма контейнеров (C4)

Ниже описана общая схема MVP. Файл с PlantUML-диаграммой — [**container_mvp.puml**](diagrams/container_mvp.puml).

**Основные контейнеры**:
1. **Веб-портал**: фронтенд-приложение, где пациент видит расписание и оформляет запись.
2. **Сервер приложений** (Backend): обрабатывает бизнес-логику (создание записи, уведомления, валидация).
3. **База данных**: централизованное хранилище информации о пациентах (включая их персональные данные) и расписания. Предполагается шифрование (TDE или на уровне колонок).
4. **Сервис уведомлений**: отправляет оповещения (email/SMS/push) администратору ресепшена при новой записи.
5. **Администратор (ресепшен)**: получает уведомление и заходит во внутренний интерфейс для подтверждения и управления расписанием.
6. **Корпоративная почта** (или push-сервис) для доставки уведомлений.

## 3. Хранение данных и политика уничтожения

1. **База данных**:
  - Все персональные поля (ФИО, контактная информация) и медицинские данные помечаются как чувствительные и шифруются.
  - Доступ к БД — только через сервер приложений, прямое подключение запрещено.

2. **Передача данных**:
  - Веб-портал доступен по HTTPS (TLS 1.2/1.3).
  - Соединение между сервером приложений и БД — шифрованное (SSL/TLS).
  - Уведомления администратору — с минимальным набором ПДн (например, только имя пациента и дата приёма).

3. **Уничтожение конфиденциальных данных**:
  - После достижения срока хранения (например, 5 лет для мед.данных или иного, прописанного в регламентах) записи автоматически удаляются или архивируются с обезличиванием.
  - По запросу пациента данные могут быть удалены (если это не противоречит законодательству).
  - Резервные копии также шифруются и удаляются по расписанию.

---

## 4. Безопасность (RBAC/ABAC, аудирование)

1. **RBAC/ABAC**:
  - Роли: «Пациент» (видит только свои записи), «Администратор» (видит все записи, но не мед.истории), «Врач» (в перспективе — видит историю пациентов, у которых он лечащий врач).
  - Используется механизм атрибутов (ABAC), чтобы медицинские поля были доступны лишь роли «Врач» при совпадении идентификатора пациента.

2. **Тегирование данных**:
  - Поля в БД помечаются тегами (PII, Medical). Система при внедрении новых функций обращает внимание, что «Medical»-данные не должны быть доступны роли «Администратор», только «Врач».

3. **Аудит и мониторинг**:
  - Все операции (запись, просмотр, изменение) пишутся в логи.
  - В логах отражаются время, пользователь, тип данных, действие.
  - При нетипичном поведении (массовой выгрузке и т.п.) — система генерирует алерт.

---

## 5. Преимущества и резюме

- **Единая точка входа**: Пациент записывается через портал, данные сразу попадают в защищённую БД, администратор видит запись в системе — без лишних Excel/почты.
- **Меньше утечек**: Шифрование на уровне транспорта (HTTPS/TLS), хранение данных в зашифрованном виде, разграничение ролей.
- **Аудит**: Любое чтение и изменение данных логируется. Возникает сдерживающий фактор для сотрудников.
- **Готовность к росту**: Система легко масштабируется, если откроются новые филиалы.
- **Соответствие законам**: Реализованы принципы Data Minimization (собираем лишь нужное), Privacy by Design, учитываем запросы на удаление (в рамках требуемых норм).
